## What this is

A fantasy league for predicting real events, played entirely over iMessage. Friends text one AI agent, bet play money on real Polymarket questions at live odds, and the agent keeps score and tells each player what the others are doing.

It is a hackathon project for HackNC (UNC Chapel Hill), entered in the sponsor track "Best iMessage Agent with Photon". The track requires integrating Spectrum, Photon's open-source messaging framework. That requirement is why the project is TypeScript.

## Photon constraints that shape the design

These come from Photon's docs and pricing page, read on October 10.

- **Shared numbers.** On the Free and Pro plans the agent has no single phone number. Photon assigns each user a number from a shared pool, so the agent's number can differ per player. Identify players by their own phone number, never by the agent's.
- **No group chats.** Shared-pool lines cannot create group chats and do not receive group events. Every player has a private one-on-one thread with the agent. A league is a row in the database, and "broadcasting" means sending a separate message to each member.
- **Limits.** Pro allows up to 100 users. Default quotas are 5,000 messages per server per day and 50 new conversations started per line per day.
- **Runtime.** The cloud transport uses Node-compatible gRPC, so edge and worker runtimes will not work.
- **Unknown.** How a brand-new person gets connected to the agent on the shared plan is not documented. Gabriel is asking Photon. Until it is answered, do not assume a stranger can simply text in.

Spectrum calls this project relies on, all from the docs:

## Architecture

One process does everything. For each incoming text:

1. Spectrum delivers the message and the sender's phone number.
2. The server finds or creates the user, then loads their league and last ten messages.
3. That context and the tool list go to the LLM.
4. The LLM picks a tool. The server runs it and fills in the user and league itself.
5. The LLM writes the reply, sent with a typing indicator.
6. If the action is visible to the league, the server messages the other members.

Every minute, a background loop refreshes prices for markets with open picks, sends a nudge when a price has moved sharply, and settles resolved markets.

Three rules that must hold everywhere:

1. **The LLM talks; code counts.** All money, share and ranking arithmetic is plain TypeScript. The LLM never computes or invents a number, and never states a price that did not come from a tool result.
2. **The LLM never chooses the user or the league.** Both come from the sender's phone number, set by the server. This is what stops one league from reading or changing another's data, including when the model is confused or manipulated.
3. **Confirm before saving a pick.** The agent states the market, the price and the stake, and waits for a yes.

### LLM tools

| Tool | What it does |
| --- | --- |
| `search_markets(query)` | Returns open matching markets with prices |
| `place_pick(market_id, outcome, stake, confidence)` | Checks cash, deducts the stake, saves the pick |
| `get_portfolio()` | Cash plus open picks at current value |
| `get_leaderboard()` | League members ranked by total value |
| `create_league(name)` | Creates a league and returns its join code |
| `join_league(code)` | Adds the sender to a league with starting cash |

Handle the exact words "leaderboard", "portfolio" and "join CODE" by keyword before calling the LLM. It is faster and removes a failure mode from the demo.

## Data model

```sql
users        (id, phone UNIQUE, name, active_league_id)
leagues      (id, name, join_code UNIQUE, starting_cash, created_by)
memberships  (user_id, league_id, cash, PRIMARY KEY (user_id, league_id))
picks        (id, user_id, league_id, market_id, token_id, question, outcome,
              stake, shares, entry_price, confidence,
              status,          -- open / won / lost
              payout, created_at)
markets      (market_id PRIMARY KEY, question, outcomes, last_prices,
              resolved, winning_outcome, updated_at)
messages     (id, user_id, role, text, created_at)
alerts       (user_id, market_id, last_fired_at)   -- cooldown for nudges
```

- Cash sits on `memberships`, not `users`, so each league has its own balance.
- `markets` is a shared price cache with no league column, because prices are the same for everyone.
- Starting cash is $1,000 and each player is in one league at a time. Both are assumptions Gabriel has not confirmed.
- The schema already supports several leagues per player. That feature is a stretch goal; do not build it unless asked.

## Scoring

Invested money counts. Players are ranked by total value:

```
total value = cash + sum over open picks of (shares × current price)
shares      = stake ÷ entry price
```

A Polymarket price is a probability: 62¢ means a 62% chance. Each share pays $1 if the outcome happens and $0 if it does not.

Worked example: $200 at 62¢ buys 322.6 shares. Cash drops from $1,000 to $800 and total value stays $1,000. If the price rises to 70¢ the position is worth $225.81 and the total is $1,025.81. If the market resolves in the player's favour, 322.6 shares pay $322.58 into cash.

- Placing a pick runs in one database transaction: check cash, deduct the stake, insert the pick. Two quick texts must not spend the same money twice.
- The leaderboard is computed on each request, never stored. Refresh prices for the league's markets first.
- Show the breakdown and the profit: `Maya $1,026 ($800 cash, $226 in play), +2.6%`.
- Settlement: winning picks pay `shares × $1` into cash, losing picks pay nothing, and the pick's status changes.
- Store the confidence percent on every pick. Calibration scoring (a Brier score over settled picks) is a stretch goal and needs that data.

```sql
SELECT u.name,
       m.cash + COALESCE(SUM(p.shares * <current price of p.outcome>), 0) AS total_value
FROM memberships m
JOIN users u ON u.id = m.user_id
LEFT JOIN picks p ON p.user_id = m.user_id
                 AND p.league_id = m.league_id
                 AND p.status = 'open'
WHERE m.league_id = ?
GROUP BY m.user_id
ORDER BY total_value DESC;
```

## Polymarket API

Everything below was checked against the live API on October 10. No key, wallet or authentication is needed for reads.

- Search: `GET https://gamma-api.polymarket.com/public-search?q=<keywords>`
- Refresh one market: `GET https://gamma-api.polymarket.com/markets/<id>`

The search response is a list of events, and each event holds one or more markets. A market is the thing a player bets on. One search for "fed rate cut" returned a single event with more than a dozen markets, one per Fed meeting.

Handle these four things, all observed in real responses:

1. **Double-encoded fields.** `outcomes`, `outcomePrices` and `clobTokenIds` are JSON strings inside the JSON. Each needs its own `JSON.parse`.
2. **Finished markets.** Search returns old markets too. Keep only `closed === false` and `acceptingOrders === true`. Do not use `active`; it was `true` on closed markets.
3. **Thin markets.** Skip any market whose `spread` is above 0.10. One open market showed a price of 51¢ with a best bid of 22¢ and best ask of 80¢, so its price meant nothing.
4. **Outcome labels.** Read labels from `outcomes` instead of assuming Yes and No. Sports markets can differ.

Search is keyword-based. The system prompt should tell the LLM to send two or three plain keywords, not the player's whole sentence. When several open markets match, the agent shows up to three and asks which one.

The search result already includes prices, so the Gamma API alone is enough. The CLOB API (`clob.polymarket.com`) is only needed for second-by-second prices and is out of scope.

**No real trading, ever.** Placing real orders needs a funded wallet key and brings age and jurisdiction restrictions. This project uses play money only. Do not add order placement, wallets or authentication against Polymarket.

## Scope

In the MVP:

1. Onboarding: first text, the agent asks for a name, then offers to create or join a league
2. Finding a market from a plain-English request
3. Placing a pick with a stake and a confidence percent
4. Portfolio and leaderboard
5. Broadcasting each pick to the other league members
6. One proactive nudge when a held market moves sharply

Stretch, in priority order: calibration scores, cashing out early, a weekly recap, several leagues per player.

Out: real money, real group chats, any web or mobile UI.

## Edge cases the agent must handle

| Case | Behaviour |
| --- | --- |
| Ambiguous request | Show up to three markets and ask which one |
| Not enough cash | State the balance and offer a smaller stake |
| Any pick | Confirm market, price and stake before saving |
| Two quick texts | Transaction prevents double spending |
| Polymarket unreachable | Say so; never guess a price |
| Closed or resolved market | Refuse and suggest a similar open one |
| Stale price | Refetch if the cached price is over a minute old before accepting a pick |

Phone numbers are used only for routing. Leaderboards and broadcasts show display names, and one member's number is never sent to another.
